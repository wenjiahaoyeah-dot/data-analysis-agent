# 自主数据分析 Agent：Spider 适配评测

## 1. 可以得出的结论

2026 年 11 月 1 日，对当前项目的自主工具 Agent 使用 DeepSeek Flash 进行了一次 Spider 1.0 开发集的适配抽样测试。预先抽取 50 道题，其中 34 道通过 SQLite → CSV → DuckDB 参考答案一致性预检；这 34 道的主要 SQL 严格结果匹配为 **5/34（14.7%）**。另外使用同一个 Flash 模型作为裁判，对 34 条最终回答各独立评分两次，两次各有 **33/34** 在正确性、完整性、证据支撑三个维度全部获得通过，两次三维判定一致率为 **34/34**。

两类数字衡量的东西不同：前者要求主要 SQL 结果的列和完整行匹配，后者是对自然语言最终回答的模型打分。**33/34 是未经过人工标注校准的同模型裁判打分，不是经验证的真实回答准确率；34/34 只表示同一裁判重复评分的一致性，不是与人工专家的一致率。** 这次评测是小样本、公开开发集、非官方适配实验，不能与 Spider 官方排行榜横向对比，也不能据此宣称生产环境准确率。

> 版本说明：本次真实模型调用发生在后续移除旧分析入口之前，运行快照见下方记录；它不是移除旧路径后代码的新一轮实测。新增的投影分析仅对保存的旧结果离线重算，没有重新调用模型。

### 补充：探索性目标列投影分析

在看过原评测结果后，额外设计了一条离线排错规则：仅当 SQLite 参考结果列名与 Agent 主结果列名可以大小写不敏感地**唯一、精确匹配**时，按参考列顺序投影后比较完整行和要求的顺序；不按数值猜测列对应，也不额外过滤行。34 题中 21 题可以映射，**16/21 匹配**；另外 13 题列名无法唯一映射，单独记为无法评分，不当作通过或失败。由于规则是事后设计、可评分题存在选择偏差，16/21 只是探索性排错观察，不能替代 5/34 的原始严格指标，也不能当作预先锁定的独立测试准确率。

逐题记录见[探索性投影明细](spider_holdout50_projection_exploratory_20261101.json)，无需模型调用即可用 [eval_spider_projection.py](../../scripts/eval_spider_projection.py) 复算。已生成 [34 题人工复核工作表](Spider逐题人工复核工作表_待填写.md)，**目前尚未完成人工标注**，因此不存在人工准确率或人与裁判一致率。

## 2. 测什么，为什么选它

[Spider 1.0](https://yale-lily.github.io/spider) 是多数据库 Text-to-SQL 数据集，其[论文](https://aclanthology.org/D18-1425/)讨论跨数据库结构的复杂文本到 SQL。它适合检验本项目的 Schema 理解、SQL 生成和数据回答；但它**不直接评估**图表、多轮交互、安全性、Excel 接入、报告生成或实际业务效果，这些能力需要另建测试集。

数据取自 [Spider 数据库重托管副本](https://huggingface.co/datasets/HAL-9001/spider-databases)的开发集和 SQLite 数据库；压缩包 SHA-256：`00636695dabed6b5f4b8328a16b13e069a2f16591d5efcce57660669c85b121b`。该公开开发集包含 1,034 题，可能被模型训练或其他调试使用，不能称为隐藏测试集。使用数据时应遵守数据集许可及来源引用要求。

抽样以 `random.Random(20261102)` 从排除先前 30 道开发题的 1,004 题中抽取 50 道，题号记录在[完整运行明细](spider_holdout50_final_flash_20261101.json)中。这是按**题目索引**去重，不是按数据库去重。抽样后我们修复了日期导入、双引号适配及预检排序问题，之后对同一批 50 题完整重新执行；这些修复及此前对开发题的调试使它不能被称为预注册、完全锁定的盲测。

## 3. 测试方法

1. 将每个题目对应的 SQLite 数据库中的表分别导出为 CSV，经过项目实际的上传、清洗、DuckDB 注册流程，使用临时数据目录和 JSON 控制面，不复用用户数据。
2. 在原 SQLite 数据库执行参考 SQL；再将参考 SQL 用 SQLGlot 转为 DuckDB 方言，在导入后的 DuckDB 中执行。针对 SQLite 将未知双引号标识符作为字符串的兼容语义增加有限转换，但仍必须通过结果一致性验证。顶层有 `ORDER BY` 时按顺序逐行比较，否则按完整行多重集比较；数值相对和绝对容差均为 `1e-6`。参考结果超过 500 行、导入报错、执行报错、结果不一致的题不送 Agent，记录为不适合这次适配评测。
3. 对通过预检的题，调用项目 `run_analysis(..., mode="agent")`，不允许 Mock 降级。模型自主调用项目提供的工具，获得结果后作答；限每轮 10 次工具调用、4 次 SQL 尝试和 8 次模型调用，结果上限 500 行。150 秒预算在节点间检查，并非严格的端到端 SLA。
4. **严格 SQL 结果指标**：任务状态为成功、主要结果未截断，且主要 SQL 的结果行与 SQLite 参考完整匹配；列按位置比较，额外列判不匹配。模型通过 `select_result` 选择主要结果；未选择时采用最后一次查询。该指标既可能把“正确答案外附了额外列”判失败，也不能单独证明最终文字回答正确。
5. **回答评分**：将问题、完整参考结果、回答及各查询最多 30 行的证据预览交给 Flash 裁判，按正确性、完整性和证据支撑三项分别输出 0/1/null 与理由。相同答案各独立评分两次、任务顺序打乱；模型输出不合法、HTTP 失败、证据超长等不作为合格评分。裁判与被评 Agent 使用同一家供应商和同一模型，存在自我偏好和共同错误风险；没有人工标注或独立裁判校准。裁判实现见 [judge_spider_answers.py](../../scripts/judge_spider_answers.py)。

裁判不是事实真值。LLM 裁判可能受位置、篇幅和自我偏好等因素影响，可参见 [LLM-as-a-Judge 研究](https://arxiv.org/abs/2306.05685)。本实验并未验证这些偏差的大小。

## 4. 实测结果

| 项目 | 结果 | 应如何理解 |
| --- | ---: | --- |
| 随机抽样 | 50 题 | 公开 Spider dev，英文问题，非数据库隔离 |
| 预检通过 | 34/50 | 可用于本次 CSV/DuckDB 适配测量 |
| 预检排除 | 16/50 | 7 题结果不一致，5 题 DuckDB 分组约束错误，4 题 SQLite 文本解码错误；不是 Agent 的错误数 |
| Agent 返回 success 状态 | 34/34 | 接口状态，不等于正确；第 345 题 success 但未答出 |
| 主要 SQL 严格匹配 | 5/34（14.7%） | 一次运行、严格列和完整行比较，额外字段亦判不匹配 |
| Flash 裁判三项全部通过，第 1 次 | 33/34（97.1%） | 同模型自评、未人工校准，不能写成真实准确率 |
| Flash 裁判三项全部通过，第 2 次 | 33/34（97.1%） | 对同一批回答的重复评分，不是再运行 Agent |
| 两次裁判三维判定全部一致 | 34/34 | 重复性观察，非人工一致率，样本较小 |
| Agent 延迟 | 中位数 5.50 秒，均值 6.05 秒 | 包括网络和模型执行，非 SLA |
| Agent 模型用量 | 输入 294,636；输出 20,632；合计 315,268 tokens | 以接口返回汇总；不包含评测适配和裁判调用 |
| 重复裁判用量 | 输入 74,808；输出 4,700；合计 79,508 tokens | 共 68 次 Flash 裁判评分；账单以服务商为准 |

运行配置为 `deepseek-flash`；裁判为同一模型的非思考模式、temperature 0。Agent 配置 temperature 0，但 DeepSeek 的思考模式可能不遵守该采样参数，因此不能声称结果确定。运行环境为 Python 3.13.12、LangGraph 1.2.19、DuckDB 2.0.0、SQLGlot 30.27.0、Pandas 3.1.0；与仓库 Docker 锁定环境可能不同。在线模型别名及服务行为未来也可能变化。

## 5. 为什么两个分数差距很大：逐题例子

- **第 47 题**：问题是最年轻狗的体重。参考为 `9.3`；Agent 查出包含多列和其他宠物的明细，自然语言正确答 `9.3`。严格 SQL 因额外列及行不匹配而失败，裁判给回答通过。该例说明 SQL 严格不匹配并不必然代表文字答错。
- **第 345 题**：参考答案为 `CV`。Agent 用尽 SQL 次数后明确表示无法完成判定，但任务状态仍为 success；两次裁判均判三维不通过。该例说明 success 不等于任务完成。
- **第 591 题**：原始日期是 `November14,2008` 之类的文本；SQLite 参考 SQL 按文本排序，Agent 则先解析日期并按时间排序，两种顺序不同。裁判认可了时间顺序。该例同时表明参考 SQL 自身可能没有充分反映问题语义，不能机械认为任一种分数绝对正确。
- **第 111 题**：模型文字称“精确匹配”，实际 SQL 使用的是 `LIKE '%amc hornet sportabout%'`；裁判仍给证据支撑通过。这是模型裁判漏检口径不一致的具体例子，说明高分不等于事实和过程均可靠。
- **第 669 题**：参考数值为 309,445，回答给出正确数值，但标题直接写“美元”，随后又承认数据未提供币种；两次裁判仍给证据支撑通过。币种是否有数据之外的依据需要复核，不能因数值正确就判整段回答完全有依据。
- **第 725 题**：参考 SQL 对 `GovernmentForm` 使用 `= 'Republic'`，结果约 50.84；回答将包含其他共和形式的 51.06 放在主结论，同时列出精确匹配口径的 50.84。两次裁判均通过；两种口径孰优需要题意和标注规范裁定，不应只看到答案包含参考数值就自动判定。

这些是基于已有题目、答案和 SQL 的 AI 辅助复查提示，**不构成人工标注，也不能据此计算人工准确率**；完整复核仍需逐题查看结果与原始数据。

在本次检查中还发现导入问题：Pandas 对 `November14,2008` 一类字符串的宽松解析可能生成公元 1 年的日期。现已改为仅在所有非空值明确符合 ISO 风格日期格式且都成功解析时自动转换；其他文本保留原值，避免静默改写。该行为会让部分非 ISO 日期保留为字符串，后续查询如需日期排序需显式解析。

## 7. 后续研究建议

扩大样本，预先固定且按数据库划分开发/测试集；同 SQLite 执行环境下运行官方协议作可比基线。建立人工双标和仲裁集，衡量裁判与人的一致率；使用独立裁判或交叉模型评估、重复多次运行，报告置信区间。单独构造中文业务问题、跨表关联、澄清、无数据、安全攻击和图表正确性测试，并人工核对参考 SQL 的语义与排序。评测结论应由可复核的实验支持，而不是挑选高分或修改结果。
