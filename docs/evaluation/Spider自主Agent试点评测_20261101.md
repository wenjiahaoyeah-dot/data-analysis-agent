# Spider 开发集自主 Agent 试点评测与代码检查

> 历史记录：本文记录修复前的一次开发试验，后续已修复文中的部分问题，并发现预检还需比较排序及处理日期导入问题。后续评测请参见同目录的最终评测报告；不要把本文当作当前版本的评测结果。

## 结论和适用范围

本次是 **Spider 1.0 开发集的随机抽样与跨数据库适配试验**，不是官方 Spider EX 评测，不是独立隐藏测试集，也不与官方排行榜分数直接比较。2026-11-01 一次运行中，随机抽取 30 题；其中 14 题未通过 SQLite→CSV→DuckDB 的参考答案可比性预检，余下 16 题进入真实模型调用。按下文定义的“任务成功且最后一次 SQL 结果整行匹配”严格规则，2/16 通过（12.5%）。16/16 返回了 success 状态，说明接口运行状态不能代表答案正确。

这个 12.5% **不是 Agent 自然语言回答的准确率，也不是 Spider 官方执行准确率**。Agent 可能先查出答案、再做辅助查询，使最后一次 SQL 与答案无关；它也可能返回额外列或自然语言给出正确答案。样本少、预检排除比例高、没有多次重复或人工逐题评审，结果只能作为开发试验的局部案例，不能概括完整数据集或实际业务表现。

## 数据集、来源和抽样

- 数据集：[Spider 官方项目](https://yale-lily.github.io/spider)、[原始论文](https://aclanthology.org/D18-1425/)、[官方代码和格式说明](https://github.com/taoyds/spider)。原数据以 SQLite 为执行环境；Spider 网站标明数据采用 CC BY-SA 4.0。
- 本次开发集题目和 SQLite 文件来自 [Spider 数据库重托管副本](https://huggingface.co/datasets/HAL-9001/spider-databases)，压缩包 SHA-256：`00636695dabed6b5f4b8328a16b13e069a2f16591d5efcce57660669c85b121b`。从原公开数据重托管，不是隐藏测试集。
- 开发集共 1,034 条，采用 Python `random.Random(20261101).sample(range(1034), 30)`，按原索引排序执行。抽样在模型运行前确定，完整索引和每题记录见 [JSON 明细](spider_dev_pilot_20261101.json)。
- 按随机样本中每个数据库导出 SQLite 表为 CSV，再调用项目现有 `create_dataset` 接口清洗、导入 DuckDB。各题原参考 SQL 同时在原 SQLite 和经 SQLGlot 转换后的 DuckDB 中执行：两者完整结果多重集不一致、参考结果超过 500 行、导入或参考执行报错时，记为**不适合此次适配评测**，不送模型；原因在明细中保留。
- 这种预检筛选受到数据库方言、数据类型和导入处理影响，排除并非随机，因此剩余 16 题不能代表全部 Spider。

## 评分和结果

对预检通过的题目，以项目 `run_analysis(..., mode="agent")` 返回的 **最后一次成功 SQL** 的结果作为候选：要求任务状态为 success、结果未截断、结果行和列值顺序与 SQLite 参考结果一致；若参考 SQL 顶层有 `ORDER BY`，还比较行顺序，否则按完整行的多重集比较。列别名不参与比较，额外列会导致不匹配。该评分规则有明确局限，特别是无法识别正确自然语言答案或正确的中间查询。

| 指标 | 结果 | 含义 |
| --- | ---: | --- |
| 预先抽取 | 30 | Spider 1.0 dev 随机题目 |
| 预检通过并请求模型 | 16 | SQLite 参考结果与转换后 DuckDB 参考结果一致 |
| 未进入模型 | 14 | 格式、方言、数据差异或结果上限等原因 |
| Agent 返回 success | 16/16 | 程序状态，非正确率 |
| 最终 SQL 严格行匹配 | 2/16（12.5%） | 仅是上述条件下的试点指标 |
| 耗时 | 中位数 4.15 秒；均值 5.32 秒 | 16 次请求的本机实测，含模型网络耗时，不代表服务 SLA |
| 模型用量 | 输入 97,615；输出 9,324；合计 106,939 tokens | 模型接口返回并由程序汇总，不能据此单独推算账单 |

排除的 14 题包括：7 题 SQLite 双引号字符串在 DuckDB 转换后按标识符解析；2 题 SQLite 容许但 DuckDB 拒绝的分组查询；3 题参考结果不一致；1 题 SQLite 源文本解码失败；1 题参考结果超过 500 行。各题的原始异常见 JSON；这体现适配器和两种数据库的差异，并不能直接归因为模型能力。

## 为什么不能把这个比例写成“回答准确率”

- 第 88 题询问大洲数量，参考结果为 `[[5]]`；模型自然语言答复是 5，但最后一次查询返回大洲明细，严格规则判失败。
- 第 290 题问奖金总额，参考是 `[[19500.0]]`；模型文字报告了该金额，但最后查询同时返回数量、总额和均值三列，因额外列判失败。
- 第 59 题参考结果为空，模型最后文字说明无人同时养猫和狗；其最后一次 SQL 是辅助统计，因此也被当前规则判失败。

这些例子表明接下来应把“SQL 精确结果匹配”“自然语言答案正确性”“最终答案与证据一致性”分开定义和评分，辅以人工逐题复核；不能只从接口 success 或任意一条 SQL 推断任务正确。

## 当前代码检查发现

1. `app/agent/tool_agent.py` 的 `_is_data_evidence` 通过字符串包含 ` from ` 且返回行数大于零判断证据。复现：`SELECT ' from ' AS x` 返回 1 行即可被视为证据；真实表查询返回 0 行却不算证据。只问 Schema 也不满足最终答复门槛，已经与现有 5 题开发脚本的结构问答预期冲突。
2. `_normalize_sql` 对整个 SQL 字符串 `.lower()`，会把字符串常量 `'A'` 与 `'a'` 变成相同签名；在大小写敏感数据上，两个不同查询可能被误判成重复调用。
3. 多次查询时对外兼容字段采用最后一次成功结果，这可能是辅助查询，不一定是回答用户问题的证据。第 88、59 题展示了评分和结果展示都可能受到影响。
4. 图执行异常时返回 `initial` 状态，已发生的工具调用、token 和轨迹可能丢失；应对错误保留可获得的中间观测并验证失败路径。

本次没有在试验中修改上述业务逻辑，以便成绩对应同一代码状态。针对本次改动的 Agent、评测、SQL 校验与租户测试共 77 项通过；测试覆盖的行为不等于生产安全或模型答案准确。

## 后续实验建议

先冻结代码、模型、数据和评分规则；修复导入/方言适配并完整记录预检失败；采用更大、预先声明的开发/测试集与重复运行。对自然语言答案另设独立评分和人工复核；如需与 Spider 基线比较，应在同一 SQLite 数据、同一官方评测协议和完整可比任务集上运行。Spider 测的是 Text-to-SQL，不单独证明图表、多轮澄清、权限和安全能力，这些需要独立任务集与指标。
