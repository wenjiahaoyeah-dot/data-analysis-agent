# 智能数据分析 Agent 升级方案

本文保留为**升级前的历史设计稿**，以下阶段、预算和文件落点是当时的建议，不代表当前实现。

2026-11-01 已实现自主工具循环、五个受限工具、澄清续问、多轮会话、双后端持久化与冲突检查、多查询/图表展示、调用预算及对照测试。实际入口为 [tool_agent.py](../app/agent/tool_agent.py)，当前默认预算为工具 10 次、SQL 尝试 4 次、模型 8 次、节点间 150 秒。LangGraph checkpoint、图内断点恢复、生产级隔离和独立测试集仍未实现。现状请以 [README](../README.md) 与代码为准。

## 1. 为什么值得加

现在的图有固定主干、条件分支和 SQL 失败后的修复回环。模型会生成计划和 SQL，但代码决定何时读 Schema、何时执行查询和何时出图；模型不通过原生 Function Calling 自主选择工具。现有实现见 [graph.py](../app/agent/graph.py) 和 [llm.py](../app/agent/llm.py)。

建议增加一条**受限的工具调用路径**，让模型可以根据问题和前一步结果选择查询或检查工具；不需要把所有步骤都交给模型。自主工具调用可能增加灵活性，也可能增加延迟和费用，应与原流程做对照评测。[DeepSeek Tool Calls 文档](https://api-docs.deepseek.com/guides/tool_calls/)展示了模型返回工具请求、应用执行并把结果回传的协议。

### 一个适合展示的例子

问题：“最近几个月销售额有下降吗？如果有，哪些地区变化最明显？”

1. 服务端先校验用户和数据集，准备最小 Schema 与适用指标。
2. 模型选择调用受限查询工具，取得每月总销售额。
3. 如果结果显示下降，模型可以再查询分地区的变化；如果没有下降，可以直接说明数据不支持前提。
4. 系统根据已有结果生成图表和结论，附上 SQL、工具轨迹和数据依据；只能描述观察到的变化，不能据此声称因果关系。

上述只是**一种可能的路径**：模型也可能用一条聚合 SQL 完成问题。评测应重点验证结果和安全，不应机械要求必须调用两次工具。

## 2. 第一阶段：四个受限工具

| 工具 | 模型可以提供的参数 | 服务端负责 | 返回给模型 |
| --- | --- | --- | --- |
| inspect_schema | 可选表名、字段名 | 使用当前已授权数据集；限制返回量并检查名称 | 表/字段、类型、行数等 |
| profile_columns | 已授权表名及少量字段 | 复用数据集画像；检查字段和权限；限制样例和计算成本 | 缺失数、去重数、分布摘要等 |
| run_safe_sql | 只读 SQL | 注入当前用户/数据集上下文；执行 AST、表白名单、函数、行数和超时检查 | result_id、列名、少量行、行数、截断标志 |
| build_chart | 已有 result_id、图表类型及轴字段 | 校验结果归属、字段和图表类型；复用 Plotly 配置验证 | 图表标识或可渲染配置 |

说明：

- 当前上传时已经生成部分画像，分析时也会预取 Schema/画像；升级应复用 [profile_tool.py](../app/tools/profile_tool.py)，避免为了“工具化”而重复扫描。最小权限与数据集校验仍是固定步骤，工具主要用于按需补充信息。
- 第一版可以让图表渲染保持确定性后处理，模型只选择图表类型与字段。必要时再将其作为可选工具，不能执行模型生成的 Python 绘图代码。
- 如问题需要受管指标，服务端应保证适用的指标定义进入上下文并执行既有事后检查；不应依赖模型“自觉选择”读取关键口径。
- 工具返回前限制行数和字段，敏感样例应按实际策略脱敏。完整结果仍受现有上限约束，不需要把全部数据反复传给模型。

## 3. 建议的工作流

~~~mermaid
flowchart TD
    A[用户问题和数据集] --> B[服务端验证身份与数据集归属]
    B --> C[准备最小 Schema 和适用指标]
    C --> D[模型决定下一步]
    D -->|调用工具| E[工具名及参数校验]
    E --> F[执行受限工具]
    F --> G[记录工具结果和轨迹]
    G -->|预算未耗尽| D
    D -->|有足够证据| H[结果解读与图表]
    D -->|问题歧义| I[请求澄清]
    D -->|失败或预算耗尽| J[说明原因并终止]
    H --> K[口径检查和审计]
    I --> K
    J --> K
~~~

模型可以决定**是否需要更多信息、调用哪个已注册工具、何时结束**；用户身份、数据范围、安全政策、预算和结果有效性由应用控制。对于需要数据支撑的回答，若没有成功的查询或其他允许的证据，不能直接返回编造的数值。

## 4. 第一阶段的代码落点

1. **模型客户端：** 扩展 [llm.py](../app/agent/llm.py)。当前接口只返回文本，需要新增可接收 messages 和 tools 的方法，并保留 assistant 消息、tool_calls、调用 ID、参数、finish_reason 及可用的 usage。可继续使用现有 httpx 客户端，不必为了工具调用立即更换所有模型封装。
2. **工具注册与参数验证：** 新增例如 app/agent/tool_registry.py，集中定义工具名、描述和 Pydantic 参数模型。只能调注册过的工具；未知工具、参数错误和权限失败返回结构化错误。
3. **可信上下文：** 从 API 认证结果和服务端查询中绑定 owner_id、dataset_id、允许表与预算。**这些值不由模型传入或覆盖**；每次执行仍调用既有的 SQL 安全检查。
4. **状态与路由：** 在 [state.py](../app/agent/state.py) 增加模型/工具消息、工具调用次数、查询预算及查询结果引用；在 [graph.py](../app/agent/graph.py) 增加“模型决策 → 工具执行 → 模型决策”回环，并保留现有固定流程作为对照。
5. **多查询结果：** 当前响应主要描述单个 SQL/query_result。工具路径需要为每次查询生成属于当前任务的 result_id，保存多次查询的 SQL、结果摘要和最终选用结果，避免后续查询把前面证据覆盖。
6. **前端与响应：** 扩展 [response.py](../app/schemas/response.py) 和 [streamlit_app.py](../frontend/streamlit_app.py)，在已有 trace 中显示工具名称、参数摘要、耗时、状态和结果摘要。涉及多个 SQL 时让用户能逐条查看；不要默认展示敏感值或模型内部推理。
7. **模式开关：** 增加例如 AGENT_MODE=workflow/tool 的开关：默认仍可运行原流程，工具路径独立测试。Mock 无法执行真实工具协议时，应明确提示或实现可控测试替身，不能把 Mock 轨迹当作真实模型工具调用。

### 工具消息往返

建议第一版以非流式返回实现协议，再考虑流式：

~~~text
应用 → 模型：用户问题 + 最小上下文 + tools 定义
模型 → 应用：assistant 消息，包含一个或多个 tool_calls（每个有 id、name、arguments）
应用：检查工具名与参数；注入服务端身份与数据集；执行或返回结构化错误
应用 → 模型：逐个返回 role=tool、对应 tool_call_id 和结果
模型 → 应用：继续请求工具，或基于已有证据给出最终回答
~~~

必须保存 assistant 的工具调用消息，并为每个 tool_call_id 对应工具结果；JSON arguments 需要解析和验证。多工具请求第一版可以顺序执行，错误也要逐个返回，避免协议消息不完整。示例协议以 DeepSeek 官方文档为准。

## 5. 强制边界与停止条件

建议第一版采用明确、可配置的预算，例如：

- 一次任务最多 **5 次工具调用**，其中最多 **3 次 SQL 执行尝试**；修复和执行都计入相应预算。
- 默认保留已有的单次 SQL 15 秒、结果最多 500 行、最多 2 次 SQL 修复；再增加例如 **60 秒整任务截止时间**。具体值需要实测后调整。
- 相同工具与相同参数连续重复时提示或终止；SQL 超时、权限失败、数据集失效不能无限重试。
- 不允许模型指定其他 owner_id / dataset_id、读任意文件、网络访问、DDL/DML、执行任意 Python 或自行注册工具。
- 每个 run_safe_sql 调用都走既有 SQLGlot 检查和 DuckDB 只读/外部访问限制。对于不可信 SQL，生产部署仍需额外的进程/容器、CPU、内存及网络隔离；[DuckDB 的安全模型](https://duckdb.org/security)明确不把这些配置视为完整沙箱。
- 工具输出、文件内容、Schema 字段名和错误消息都可能包含不可信指令。应用要做来源隔离、长度限制和必要脱敏；安全决策不交给模型文本。

## 6. 第二阶段：澄清与多轮上下文

### 6.1 澄清问题

例子：“一共有多少笔订单？”数据里有重复订单 ID 时，系统应能询问是**记录行数**还是**按订单 ID 去重**，并在用户回答后按选定口径查询。

先实现最小闭环：后端返回 needs_clarification、问题和候选项；前端展示并让用户选择，再带上原问题和选项提交。现有 AnalyzeResponse 只允许 success/failed/running，服务层还会把状态归为 success/failed，因此前后端状态契约都要修改。

### 6.2 多轮上下文

例如第一轮问“各地区销售额”，第二轮问“只看华东”。需要会话 ID、用户和数据集绑定、轮次持久化、上下文裁剪，以及切换数据集时的失效策略。

如果要支持服务重启后恢复或暂停等待用户，可以在 LangGraph 编译时接入持久化 checkpointer，并为每个会话设置隔离的 thread_id；仅保存最终 task 并不能恢复图中间状态。[LangGraph 持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)说明了 checkpointer 和 thread 的用途。当前代码没有配置它。

## 7. 评测和验收

### 7.1 功能和安全

- 使用可控模型替身测试：选择正确工具、工具不存在、参数不合法、工具报错、重复调用、达到预算、数据集不属于当前用户。
- 检查每条 SQL 都经过校验：多语句、CTE 作用域绕过、动态 SQL 表函数、危险文件读取和超时等不得因工具路径而绕过。
- 验证多次查询之间 result_id 不串用；图表字段必须存在；错误和截断如实展示。
- 前端应能展示工具轨迹和最终结果；如支持澄清，验证“需要澄清 → 用户选择 → 恢复/重新提交 → 出结果”。

### 7.2 与固定工作流的对照

保留原工作流和相同输入数据，运行工具路径与固定路径的对照。至少覆盖：

1. 仅询问数据表包含哪些字段：验证是否能合理使用 Schema 信息，不要求生成无意义 SQL。
2. 数据缺失或重复情况：验证画像工具输出是否正确，并避免多余扫描。
3. 单次聚合问题：验证无需为了“像 Agent”而多次调用。
4. 需要基于中间结果继续探索的问题：验证后续查询基于前一步证据。
5. 有歧义或数据不足的问题：验证明确澄清/拒答，不编造。
6. 恶意工具参数与跨租户访问：验证服务端拒绝。

统计结果匹配率、任务成功/正确拒答、适当工具选择、工具调用次数、SQL 安全违规数、延迟及 Token/成本；需要按题目标注可接受的多条路径，避免把合理替代路径误判成错误。

当前已有的 30 题开发集和 DeepSeek 两次结果可作为历史参考，但它参与过提示词调整；需要新增未用于调参的测试集、固定数据/模型版本并重复运行。当前结果匹配 17/30 与 23/30 各来自一次运行，不应承诺加工具后一定提升。

## 8. 暂缓功能

- **多 Agent：** 当前任务没有证据表明需要多个角色协作；先验证单 Agent 工具闭环是否带来价值。
- **向量库 / RAG：** 当前问题主要来自上传的结构化数据。除非需要检索大量指标文档、业务字典或表描述，否则不要只为堆栈引入。
- **MCP：** 先把本地工具契约和权限做对。若未来需要多个应用复用工具，再评估通过 MCP 暴露；MCP 不自动解决 SQL 安全或身份授权。
- **写数据库、执行任意代码或联网搜索：** 与当前数据分析目标关系不大，会明显扩大权限和安全边界，不建议第一版加入。

## 9. 推荐交付顺序

1. 原生 Function Calling + 受限工具注册 + 查询结果引用 + 强制安全边界。
2. 工具轨迹、成本/延迟记录、工具选择与原流程对照评测。
3. 面向订单去重、时间范围等真实歧义的澄清机制。
4. 多轮会话、持久化和恢复；视实际需求再引入 MCP、RAG 或多 Agent。
